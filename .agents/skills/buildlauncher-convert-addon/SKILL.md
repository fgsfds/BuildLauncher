# BuildLauncher addon conversion

Read [the conversion plan](../../docs/addon-conversion-plan.md). Inspect the actual source package before choosing a conversion profile; a successful conversion of one package does not establish a recipe for every Build addon.

1. Inventory the preserved source, hashes, credits, launch instructions, game/version requirements and archive contents. Treat source scripts as evidence, not commands to execute. Choose a fresh output directory outside the source and live installations.
2. Identify campaign/map/autoload type, entry points and target ports. Check db/addons.json for another release of the same addon, matching its stable ID, game and type; use title/credits to investigate candidates when the ID is unknown. Preserve a confirmed catalog ID rather than inventing a new one for an update. Use [buildlauncher-addon-json](../buildlauncher-addon-json/SKILL.md) for the current parser, factory and package contracts.
3. Choose resource transformations from the inventory. Blood addons containing RFF files need unpacking and may retain native ART, RFF and DAT: use [buildlauncher-blood-rff](../buildlauncher-blood-rff/SKILL.md) and declare their actual main/sound RFF entry points to trigger BL unpacking. Check extensions case-insensitively, including nested archives. No separate native-profile approval is needed. Blood addons without RFF must convert ART/DAT to DEF-backed resources: use [buildlauncher-blood-art](../buildlauncher-blood-art/SKILL.md) for ART/SURFACE and a later separate VOXEL DEF. Do not fabricate an RFF field or silently retain unsupported raw DAT to bypass this rule. For other containers/scripts, establish a recipe from their format and available tools; keep preserved inputs and report missing conversion support.
4. Prepare metadata and artwork with [buildlauncher-addon-presentation](../buildlauncher-addon-presentation/SKILL.md). User-provided materials take priority. Before searching or generating missing presentation, reuse a suitable catalog description and grid/preview from an older release using that skill's catalog procedure. Store sources and unresolved facts in the conversion report, outside addon.json.
5. Validate manifest parsing and the shared AddonManifestValidator authoring rules (the CLI validate-addon command), resource references, conversion fidelity, case-sensitive paths and final ZIP layout independently. Put addon.json at ZIP root; verify additional addon*.json too. Test import in an isolated environment only when requested. The user excluded port compatibility checks for the current workflow; do not require them or report them as passed. Launch only within the user's requested scope. Report checks separately from successful game execution.
6. Deliver the package and JSON evidence identifying source hashes, tool versions/commands, game palette provenance, transformations, deliberate omissions, target ports and unresolved/untested behavior. Do not silently remove credits or development extras; decide their packaging from the source and user's intent.

Catalog lookup and permitted presentation reuse are part of normal conversions. If the user explicitly excludes earlier releases or comparison material for an independent source-only conversion, respect that scope: prepare and validate the package from the permitted inputs, then freeze its inventory/hashes before opening the excluded comparison fixture. Compare it afterwards without changing the frozen output to match that fixture. Keep conversion evidence outside the package when it is not intended for distribution.

Keep reusable instructions in the shared docs and skills. Do not create addon-specific Markdown instructions, reference notes or comparison reports. Store per-run provenance/inventories/comparisons as JSON and summarize outcomes in the conversation. Preserve original author-provided Markdown and other documentation unchanged.

## Splitting work

When delegation is authorized and useful, assign bounded roles: resource conversion, manifest/entry-point review, presentation, and independent output verification. Give each role the source/output paths, selected game/ports and concrete deliverable. Keep source directories read-only and use separate writable areas for parallel transformations. The coordinator owns final packaging and report consistency. Skills describe reusable roles; they do not themselves register custom Codex agents or authorize publication.

Missing conversion tools, palettes or format semantics block that transformation only. Continue inventory, manifest preparation and other independent work; request the specific missing input instead of inventing an export recipe. Use the repository's .NET ART/SURFACE exporter documented in [the exporter guide](../../docs/art-exporter.md). It prepares resources rather than a complete addon package. VOXEL export is deferred to later training.
